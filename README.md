Production Phase 2 — Communication, Code Room & Production Hardening\n\n## What Cymatic Resonance is\n\nCymatic Resonance is the realtime institutional execution layer of the Cymatic Hub ecosystem.\n\nIt is designed to coordinate:\n- institutional membership and authorization;\n- attendance and location-aware sessions;\n- realtime presence;\n- persistent communication;\n- institutional meeting rooms;\n- audio/video communication;\n- tasks and operational workflows;\n- notifications and administrative visibility.\n\n> **Every user-visible operational state must correspond to a real backend, realtime, device, network, or database state.**\n\nThere are no production claims for simulated media, simulated attendance, fake notification delivery, or frontend-only authorization.\n\n## Ecosystem\n- **Cymatic Hub:** https://cymatichub.xyz\n- **Cymatic Resonance:** https://resonance.cymatichub.xyz\n- **Cymatic Study:** https://study.cymatichub.xyz\n\n## Production architecture\n\n~~~text\nCymatic Hub\n└── Cymatic Resonance\n    ├── Identity & Access\n    │   ├── Supabase Auth\n    │   ├── Institutions / Organizations\n    │   ├── Memberships\n    │   ├── Authorized server/database event |\n| Notifications | Server-side delivery lifecycle |\n| UI | Projection of authoritative state |\n\n## Code Room\n\nCode Room is the institutional realtime collaboration surface. It is conceptually informed by familiar meeting and messaging workflows, while remaining an independent implementation.\n\nA room contains:\n- authorized members;\n- roles and permissions;\n- realtime presence;\n- persistent chat;\n- meeting state;\n- audio/video;\n- screen sharing;\n- reactions;\n- tasks;\n- attendance/session context;\n- notifications.\n\nFor institutional rooms of approximately 50 members, media architecture is based on an SFU model rather than a full peer-to-peer mesh.\n\n## Calls\n\nThe production call lifecycle separates call state from media state:\n\n~~~text\nIDLE → INVITING → RINGING → ACCEPTED → CONNECTING → CONNECTED\n                                      ↘ RECONNECTING ↔ CONNECTED\nCONNECTED → ENDING → ENDED\n~~~\n\nTerminal alternatives include DECLINED, MISSED, and FAILED.\n\nThe UI must not display “connected” simply because a participant clicked Accept. Actual media connection state is required.\n\n## Attendance and GPS integrity\n\nAttendance is a security-sensitive institutional record.\n\nThe production direction is:\n\n~~~text\nDevice\n→ GPS acquisition\n→ accuracy validation\n→ session/geofence validation\n→ server authorization\n→ attendance event\n→ database\n→ realtime administrative projection\n~~~\n\nFuture continuous-presence controls may include administrator-defined session center, geofence radius, GPS accuracy threshold, grace period, dwell requirement, check-in lock, continuous tracking policy, exit detection, absence transition, suspicious-location detection, and audit history.\n\nGPS alone cannot prove physical presence with cryptographic certainty. The system therefore uses layered evidence and explicit institutional policies rather than claiming that a single location reading is unforgeable.\n\n## Plans and entitlements\n\nOnboarding establishes an organization and its plan. Server-side entitlement checks determine capabilities.\n\nSupported plan categories:\n- **FREE**\n- **PAID**\n- **CUSTOM / INSTITUTION**\n\nThe exact limits are configuration, not hardcoded UI assumptions.\n\n## Security\n\nProduction security includes Supabase RLS, organization and membership boundaries, role and room authorization, entitlement enforcement, secure server-side functions, explicit function grants, private realtime authorization, short-lived media credentials, secret isolation, rate limiting, audit logging, and attendance integrity controls.\n\nBrowser code must never contain server secrets.\n\n## PWA, Android, iOS and desktop\n\nThe web/PWA is the canonical web client. Native distributions share the same backend and domain contracts.\n\nPlanned distribution targets:\n- installable PWA;\n- Android APK/AAB;\n- iOS application;\n- Windows desktop;\n- macOS desktop;\n- Linux desktop where justified.\n\nNative packaging is a delivery layer, not a second backend. Authentication, entitlements, room semantics, authorization, attendance rules, and domain contracts remain shared.\n\n## Architecture phases\n\n1. **Phase 0 — Foundation**\n2. **Phase 1 — Operational Core**\n3. **Phase 2 — Production Communication & Code Room**\n4. **Phase 3 — Production Administration & Security Hardening**\n5. **Phase 4 — Scale**\n6. **Phase 5 — Mobile & Desktop Distribution**\n7. **Phase 6 — Continuous Production**\n\nThe complete implementation contract is maintained in `docs/PRODUCTION_ARCHITECTURE_PHASE_2.md`.\n\n## Engineering rules\n\n1.
